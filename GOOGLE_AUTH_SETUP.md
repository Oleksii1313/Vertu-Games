# VertGames — вход и подтверждение через Google

## Что уже добавлено

- Кнопка **«Войти через Google»** во входе и регистрации на `index.html`, `top.html`, `roulette.html`, `admin.html`.
- Выбор аккаунта на официальной странице Google. Сайт **не просит пароль от Google**, не читает письма и не использует Gmail API.
- Серверный OpenID Connect authorization-code flow. После проверки Google создаётся обычная сессия VertGames; для Google-входа SMTP не нужен.
- Для нового пользователя создаётся уникальный ник вида `g_<имя>_<суффикс>`; пароль сайта не создаётся. Повторный Google-вход открывает ту же запись.
- Для имеющегося серверного аккаунта — **«Привязать Google к этому аккаунту»** в профиле. Требуются активная серверная сессия и тот же email. Пароль, ник и существующие локальные данные этого аккаунта сохраняются.
- Нет автоматического объединения аккаунтов по совпадению email. При совпадении адреса сначала войдите старым способом и выполните привязку.
- Поддерживаются подтверждённые Gmail и Google Workspace. Для Google-аккаунтов с внешней почтой, за которую Google не является авторитетным провайдером, используйте регистрацию с кодом из письма.

**Важно:** код интеграции готов, но без настоящих OAuth-настроек владельца кнопка сообщает, что вход не настроен. Она не имитирует успешное подтверждение. В поставляемом архиве нет OAuth-ключей, базы аккаунтов и паролей.

## 1. Где должен работать сайт

Нужен запущенный Python-сервер и стабильный адрес, например `https://games.example.com`. HTML, `/api/auth/*` и callback должны обслуживаться под **одним origin**.

Один опубликованный HTML, `file://`, обычный статический хостинг и встроенный предпросмотр не выполняют серверный OAuth. Простого добавления кнопки или Client ID в HTML недостаточно. Интеграция не обновляет ранее опубликованный сайт автоматически.

Для публичной версии обязателен HTTPS. HTTP разрешён только для разработки на `localhost`, `127.0.0.1` или `::1`. `PUBLIC_URL` — origin без пути, query и fragment. Размещение API под подпапкой этой реализацией не поддерживается.

## 2. Настройки в Google

В [Google Cloud Console](https://console.cloud.google.com/) откройте **Google Auth Platform** для своего проекта (либо создайте проект).

1. **Branding**: укажите название приложения VertGames, настоящий контакт поддержки, домен, ссылки на главную и конфиденциальность. Перед публичным запуском заполните реальный контакт в `tools/site-info.json` и сведения об операторе.
2. **Audience**: выберите тип аудитории. Для внешнего приложения в режиме Testing добавьте нужные Google-аккаунты в Test users. Для общего доступа настройте публикацию и выполните требования Google; готовность/одобрение приложения здесь не гарантируется.
3. **Data Access**: вход запрашивает только `openid` и `email`. Не нужны Gmail, Drive, Contacts и offline-доступ.
4. **Clients → Create client → Web application**: создайте веб-клиент OAuth.
5. В **Authorized redirect URIs** добавьте **точно**:

   ```text
   https://ВАШ-ДОМЕН/api/auth/google/callback
   ```

   Для локальной разработки отдельная запись:

   ```text
   http://localhost:8000/api/auth/google/callback
   ```

   Протокол, домен, порт, путь и завершающий слеш должны совпадать. Wildcard и случайный URL предпросмотра не заменяют зарегистрированный redirect URI.

6. Сохраните Client ID и Client secret в окружении сервера. **Не присылайте secret в чат, не вставляйте в HTML и не коммитьте в репозиторий.** При утечке отзовите/замените секрет в Google.

Этот flow делает обычный переход браузера на Google, а не использует Google JS SDK. Поле Authorized JavaScript origins не заменяет настройку Authorized redirect URIs.

Официальное руководство: https://developers.google.com/identity/openid-connect/openid-connect

## 3. Установка на сервере

Python 3.10+; ниже команды Linux/macOS:

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r requirements.txt
cp .env.example .env
```

Если `.env` уже есть, **не перезаписывайте его**: добавьте только недостающие параметры.

```dotenv
PUBLIC_URL=https://ВАШ-ДОМЕН
GOOGLE_CLIENT_ID=ВАШ_CLIENT_ID.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=ВАШ_СЕКРЕТ_ТОЛЬКО_НА_СЕРВЕРЕ
```

Затем загрузите переменные окружения и запустите:

```bash
set -a
. ./.env
set +a
python3 server.py
```

`server.py` сам файл `.env` не читает. На хостингах с разделом Environment Variables задайте параметры там. Для автоматического перезапуска используйте менеджер процессов вашего хостинга; не полагайтесь на открытый терминал.

SMTP-параметры остаются независимыми: нужны для прежней регистрации письмом, но **не нужны для Google**. Без зависимостей Google существующий сервер писем продолжит работать; Google-вход будет считаться ненастроенным.

Сервер создаёт таблицы `google_identities` и `google_flows` автоматически, не удаляя существующие таблицы/аккаунты. Перед обновлением сделайте резервную копию SQLite. Храните `data/` на постоянном диске и не заменяйте её пустой папкой при деплое.

Публичный allowlist не выдаёт `google_oauth.py`, `.env`, SQLite и `requirements.txt`. При размещении за другим веб-сервером не раздавайте весь исходный каталог без ограничений. Callback должен доходить до Python, а не возвращать `index.html` от статического fallback.

## 4. Проверка настоящего входа после настройки

1. Откройте сайт в отдельной вкладке, не в sandboxed iframe.
2. На странице API нажмите проверку: Google должен отображаться как настроенный. Это проверяет **наличие конфигурации**, а не её правильность в Google Console.
3. Нажмите «Войти через Google», выберите разрешённый тестовый аккаунт. После возврата должен появиться профиль с подтверждённой почтой.
4. Выйдите из VertGames и войдите тем же Google-аккаунтом: ник должен остаться прежним.
5. Проверьте отмену на странице Google: новый аккаунт и сессия создаваться не должны.
6. Для старого серверного аккаунта войдите паролем → профиль → привязка → выберите тот же email. Проверьте затем оба способа входа и сохранение ника.

### Старые локальные аккаунты и игровой прогресс

Google не переносит localStorage между устройствами. Баланс, покупки и карьеры остаются в текущем браузере и привязаны к игровому аккаунту.

Если аккаунт ещё только локальный, сначала используйте существующий перенос с подтверждением почты в профиле, затем привяжите Google. Иначе первый Google-вход создаст **отдельный** серверный профиль с другим ником. Старый локальный аккаунт автоматически не удаляется, но его прогресс не превращается в прогресс нового профиля.

## 5. Ошибки

| Сообщение / код | Что проверить |
|---|---|
| GOOGLE_NOT_CONFIGURED | Зависимости, PUBLIC_URL, Client ID и secret в окружении запущенного процесса; перезапуск после изменения. |
| BACKEND_UNAVAILABLE | Работает ли Python, доступен ли `/api/auth/session`, не возвращается ли HTML вместо JSON. |
| redirect_uri_mismatch на Google | Точное совпадение URI в Google Console и `PUBLIC_URL + /api/auth/google/callback`. |
| access_denied / ограничение аудитории | Test users, аудитория и статус приложения в Google Console. |
| GOOGLE_STATE_INVALID | Истёкшая попытка, потерянные cookie, другой браузер/домен или повтор старого callback. Начните заново. |
| GOOGLE_TOKEN_FAILED | Настройки клиента/секрета, время сервера, HTTPS, доступ сервера к Google. Детали токенов намеренно не выводятся. |
| GOOGLE_ACCOUNT_EXISTS | Войдите в существующий аккаунт прежним способом, затем явно привяжите Google. |
| GOOGLE_LINK_EMAIL | Выбран другой email. Нужен адрес текущего серверного профиля. |
| GOOGLE_LINK_SESSION | Во время привязки изменился аккаунт/сессия либо был выполнен выход. |
| GOOGLE_EMAIL_EXTERNAL | Внешний адрес Google-аккаунта: используйте подтверждение письмом. |
| GOOGLE_LOGIN_REQUIRED | Это Google-only аккаунт без пароля сайта. Нажмите Google-кнопку. |

## 6. Защита и данные

- Одноразовый случайный `state`, HttpOnly browser-binding cookie, серверный `nonce`, PKCE S256, срок попытки 10 минут.
- Начало — same-origin JSON POST; URL возврата выбирается из фиксированного списка страниц. Нет произвольного `returnUrl` или открытого redirect.
- Callback обменивает код на фиксированном Google token endpoint. Официальная библиотека `google-auth` проверяет подпись ID token, audience, issuer и срок; дополнительно проверяются nonce, authorized party, email verification и идентификатор subject.
- Идентичность — `sub`, не присланный браузером email. Клиентские JWT/email не принимаются для прямого входа.
- Google-only запись имеет маркер `!google-only`, который не проходит проверку пароля. Никаких общих/случайных паролей для входа не создаётся.
- ID/access tokens и authorization codes не сохраняются в SQLite, localStorage или логах приложения; refresh token не запрашивается. Секрет остаётся на сервере. Google subject и связь с пользователем хранятся в SQLite.
- Временные OAuth-записи удаляются после обработки callback; просроченные очищаются при новом старте входа. HttpOnly flow-cookie очищается после callback. Серверная сессия VertGames сохраняет прежний срок до 30 дней.
- На HTTPS flow-cookie имеет префикс `__Host-`; сессионная cookie получает Secure от настроенного PUBLIC_URL.
- Логи Python исключают query string. Настройте **прокси/хостинг** аналогично: не журналируйте callback `?code=…` и заголовки Cookie/Authorization.
- Выход из VertGames не разлогинивает Google. Отзыв разрешения в Google не удаляет SQLite-запись и не гарантирует немедленного закрытия уже выданной сессии VertGames. Самостоятельное отвязывание/удаление пока не реализовано; нужен владелец сервера.

## 7. Что протестировано в рабочей среде

`python3 -m unittest discover -s tools -p test_google_auth.py -v` — автоматические HTTP-тесты с временной SQLite и **синтетическими** ответами провайдера: создание/повторный вход/выход; запрет пароля Google-only; state, browser binding, replay и срок; отмена; неверные nonce/issuer/audience/azp/время/email; Workspace; запрет неявной привязки; явная привязка с сохранением записи и старого пароля; чужая почта/потеря сессии; origin, whitelist redirect, скрытые файлы и отсутствие секрета в ответах.

Также проверен прежний поток регистрации с кодом и входом по паролю, с подменой отправки SMTP только внутри теста.

Отдельный тест реальной криптографической проверки использует синтетическую RSA-пару: принимается правильная подпись, отклоняются чужая подпись, audience, issuer и просроченный токен. Для этого теста опционально нужен пакет `cryptography`; без него именно этот тест пропускается. Это **не** подтверждение успешного входа в настоящий Google.

В Chromium проверены четыре страницы, RU/EN, размеры 320/390/844/1366, недоступный/ненастроенный backend, отмена, запрет имитации успеха одним URL-параметром, восстановление синтетической подтверждённой серверной сессии с сохранением баланса и очисткой pending-флага, переход на Google URL. Физический телефон/Safari не проверялись.

**Реальный Google OAuth end-to-end пока не проверен:** владелец ещё не предоставил настроенное развёртывание и OAuth-клиент. После настройки выполните раздел 4.
